# Rust Powers plugin quality audit

**Keep the nine-skill design. Fix the guidance that changes runtime behavior, then repair the measurements used to decide what earns space in a skill.** The two highest-impact examples are an optional NATS dependency that can prevent HTTP startup and a payment recipe that loses caller isolation at the provider. A compiler can accept both patterns. The existing ownership split already puts each correction in one place.

Rust Powers **0.11.0** at [`562bee5`](https://github.com/DenysMoskalenko/rust-powers/tree/562bee5793f3e503e2dfa28effd8fd90f4b8df3a) matched GitHub’s `main` on 20 November 2026. The review covered every skill entry point and reference index, selected implementation paths and their evals, the scaffold, manifests, verification scripts, saved model results and official host guidance. The NATS and Redis findings come from tracing the shipped examples. The Rust and eval-reporting findings below also have offline reproductions.

## Fix the examples that can change production behavior

### High priority — let HTTP start while optional NATS is unavailable

`retry_on_initial_connect()` returns a client that can still be pending. The recipe then awaits stream creation inside `start()`. When bounded retries run out, the function returns an error before it gives the application its messaging state. A service following this wiring cannot serve the promised `200/degraded` response while the broker is unavailable at startup. The contradiction is visible in the control flow. [Startup, lines 647–675][nats-start] · [Readiness promise, lines 789–802][nats-ready]

For the optional-broker example, let HTTP obtain its state and move stream declaration into the supervised worker with shutdown-aware retry. Preserve the distinct policy for a service that requires messaging. **Verify it** by starting with PostgreSQL healthy and NATS unavailable. Liveness and an ordinary database read succeed, readiness returns 200 with messaging degraded, and the worker starts processing after NATS recovers without restarting HTTP. Keep the response contract in its current owner. [HTTP readiness contract](../skills/axum-service/SKILL.md#operations)

### High priority — preserve payment identity across Redis and the provider

The Redis key includes the authenticated subject. The call to the shared payment provider sends the original header alone. Two customers can independently use the header `1`, obtain different Redis claims, and send the same key to the same merchant account. Adyen scopes keys at the company-account level. Depending on the provider and request parameters, a second payment can replay an earlier result or be rejected. Define a stable, provider-compatible key using an unambiguous encoding of caller, operation and client key. Make Redis Eval 5 check that contract. With a fake provider, verify that it sees one identifier across a caller’s retries and distinct identifiers for two callers reusing the same header. [Handler, lines 841–864][payment-handler] · [Redis eval](../evals/rust-redis.md) · [Adyen key scope](https://docs.adyen.com/development-resources/api-idempotency/#key-scope-and-validity-time) · [Stripe replay rules](https://docs.stripe.com/api/idempotent_requests)

The same recipe needs **a fresh ownership token per Redis claim**. The stable payment key identifies the logical payment. A claim token identifies the attempt currently entitled to update the Redis entry. The documented completion writes unconditionally and release compares a marker derived only from the request fingerprint. After expiry, a late completion can replace a successor’s entry and a late failure can release a successor with an identical fingerprint. Atomically compare the attempt token before storing or releasing. Verify that replacing a claim invalidates the previous owner’s writes and releases for equal and different fingerprints. A payment that already succeeded still returns its successful HTTP outcome if storing fails. [Completion and release, lines 736–775][claim-store] · [Marker, lines 823–829][claim-marker] · [Redis ownership guidance](https://redis.io/docs/latest/develop/use/patterns/distributed-locks/)

## Repair the evidence used to change skills

**Treat skipped graders as missing.** Replaying the saved 4 November aggregate through the current reporter printed a perfect +1.00 improvement for SeaORM Eval 8. Both baseline attempts had skipped paid graders at the cost ceiling. After the maintainer reran that baseline, the published record showed both arms passing twice, a difference of zero. The reporter averages the stored scores and only flags runs with an error. In the archived baseline, both runs had `skippedPaidGraders: true` and a null error. Add a synthetic regression case with one fully graded treatment and one skipped baseline. It should display the skipped count and an unavailable difference. Replacing the skipped baseline with a genuine pass should produce zero. The saved local aggregate is `2026-11-04T14-14-56-188Z/aggregate-result.json` under `evals/.run/cases/results/`. Passing it to `scripts/summarize_evals.py` reproduces the erroneous score without a model call. [Reporter, lines 48–55][reporter] · [Published correction](eval-results-2026-11-04.md)

**Test the grader against a plausible wrong answer.** All 94 answer regexes compiled. Twelve of 53 probes have only a negative content assertion. NATS Probe 3 asks for three status mappings. Its regex accepts “Map every NATS request failure to HTTP 500” because it only catches two forbidden spellings next to `TimedOut`. Its historical +1.00 supports avoidance of that particular mistake. Add a positive check where correctness requires a positive result. This probe’s content grader should pass the documented handling, including 503 for both `NoResponders` and `TimedOut`, and reject both the all-500 reply and an irrelevant reply. Keep purely negative probes where absence is the whole requirement. [Probe 3, lines 197–201][nats-probe] · [Grader generation](../scripts/build_eval_cases.py) · [Evaluation guidance](https://agentskills.io/skill-creation/evaluating-skills)

**Give two existing promises observable outcomes.** The generator produced 254 cases. Of its 55 judged tasks and 53 probes, 79 cases run in scaffold-derived workspaces and 29 start empty. Every generated task disables edits and commands. Greenfield Eval 1 can reward a reply describing a passing service. Give one greenfield case a disposable directory, ask for a hyphenated crate name, and have the grader independently build and test the actual files the agent produces. For the shared scope paragraph, use one small existing service with its own error type and a tuned setting. A passing change must implement the requested behavior and preserve both. The UUID experiment illustrates why fixtures matter. On an empty fixture the two UUID checks passed 2/2 with the plugin and 0/2 without. On the scaffold the arms tied on each check. [Generator](../scripts/build_eval_cases.py) · [Greenfield rubric](../evals/rust-scaffolding.md) · [UUID experiment](eval-results-2026-11-04.md)

**Protect local eval output before reruns.** The generator recursively deletes an existing path supplied to `--out` without establishing it created that directory. Reuse the verifier’s generated-directory marker and reject paths containing source trees. An unmarked temporary directory containing a sentinel must survive. A marked output directory must rebuild and preserve earlier results. This is a maintainer-tool fix. [Generator, lines 202–210][generator-out] · [Verification directory guard](../scripts/check_snippets.py)

## How to repeat the audit

1. **Freeze the evidence.** Record the commit, plugin version and host versions. Run `python3 scripts/validate_skills.py --strict` and `python3 scripts/check_snippets.py --dry-run`. Check the full snippet CI job on that same commit. Enumerate the expected names in each host affected by packaging edits.
2. **Follow one user task end to end.** Trace its description to the entry point, referenced recipe, scaffold contract and eval. Pick an outcome the compiler cannot check, such as whether reads still work when a broker starts late. Record the smallest counterexample and give the fix to the skill that owns it.
3. **Decide what evidence the change needs.** For an API error, use pinned upstream semantics or a deterministic test. For a proposed wording or length change, compare the current and proposed text on the same task, include a held-out prompt, and preserve any incident-backed behavior. Check the grader on a deliberately wrong answer first. Record which result would justify keeping the current wording.

For the next release, ship correctness fixes with matching eval text, focused regression checks and the required version bumps. Repair scoring before using its results to remove an instruction.

The September Opus 5.5 study found 172/183 expected activations and 208/209 correct exclusions among completed attempts. Seventeen attempts were excluded and two skip cases never ran. Those figures measure that cohort. The tracked near misses all name another Rust Powers skill. When testing plugin-wide over-triggering, include a realistic task where the right outcome is to load none. For a description change, restrict the run to affected triggers, their near misses and held-out phrasings. Report incomplete runs separately. For any billed experiment, name the cases, arms and total cost cap for owner approval first. No paid models were run for this audit. Installation, remote updates, present-release routing across hosts and downstream incident frequency remain unmeasured.
